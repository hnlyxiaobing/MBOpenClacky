# 开发效率指南（Development Efficiency）

> 本文档由 113 个真实开发会话（2026-06 → 2026-08，24,806 次迭代，6,660 万 tokens，总成本 $88.76）的经验数据提炼而成。
> 核心规则已固化到 `AGENTS.md` 的 **Development Efficiency Protocol** 章节，本文件提供完整数据、案例与检查清单。

---

## 1. 成本数据：钱到底花在哪

### 1.1 模型单价是最大的成本变量（不是 token 量）

| 模型 | 每迭代成本 | 相对成本 | 适用场景 |
|---|---|---|---|
| abs-claude-fable-5 | ~$0.124 | 3000× | 仅限复杂推理（架构设计、FFI 布局、对抗性评审） |
| deepseek-v4-pro | ~$0.0097 | 240× | 中等推理 |
| minimax-m3 | ~$0.0039 | 95× | 综合开发 |

| kimi-k2.7-code | ~$0.0015 | 36× | 代码任务 |
| mimo-v2.5-pro | ~$0.0006 | 15× | 执行型任务 |
| qwen3.8-max-preview | ~$0.0003 | 7× | 执行型任务 |

## 2. 高效模式（怎么做又快又好）

### P1. 机械性开发任务用便宜模型
harness/spec 开发（读 spec → 改代码 → 编译 → 测试）是执行型任务。实证：442 迭代 $0.049、605 迭代 $0.067、438 迭代 $0.083 的会话都用便宜模型完成，产出质量与贵模型会话无差异。

### P2. spec/harness 驱动流程
1. **一次并行读入所有相关 spec**（一条消息 8 个 file_reader）
2. **todo_manager 拆分任务**
3. **小步实现 + 即时验证**：`git status → moon check → git commit → git push` 循环
4. **完成后归档 spec 并更新 CHANGELOG**

### P3. 动手前先确认环境和构建方式
开发前先 `moon version && uname -a`；一次 `file_reader` 读完整 Dockerfile / moon.pkg 配置，而不是猜命令。

### P4. 用 skill 委派探索
用 `code-explorer` / codebase-memory MCP / `moon ide doc` 拿项目全景，而不是手动遍历所有包。

### P5. 批量并行工具调用
把无依赖的工具调用合并到一条消息（平均 15 个调用/消息的会话效率最高），减少往返和过渡推理 token。

### P6. 探测逻辑写成脚本文件再执行
`write /tmp/probe_*.sh → bash` 把多步验证固化成脚本，可复用、不易出错。

## 3. 浪费陷阱（怎么做会浪费时间和 token）

### W1. 模型选错 = 最大浪费黑洞（可占预算 1/3+）
最贵模型跑执行型任务 = 白烧钱。**执行型任务永远用便宜档模型。**

### W2. 挤牙膏式 grep 探索
某会话连续 9 次 grep 同一文件的不同 API，每次只 `head -10`，才拼出全貌。对 token 而言，9 次 grep + 各自上下文重传，比 1 次 `file_reader` 读完贵得多。
**正确做法**：目标文件一次读完；精确匹配跨文件才用 grep；API 发现用 `moon ide doc`。

### W3. 重复读同一份文件（压缩后忘记已读）
- `gap-analysis` 文档单会话被完整读取 4 次（16KB × 4）。
- `brand_cell.mbt` / `tasks.js` / `chat_cell.mbt` 各被读 3-4 次。
**原因**：长会话触发上下文压缩后，模型丢失"已读"记忆。
**对策**：读过大文档立即把要点写进 todo/笔记；长任务拆短会话。

### W4. 构建命令靠猜
某会话 7 次试错（`warren build` → `ls` → `cat warren.toml` → `cat moon.pkg` → `moon build --target js` → `cat moon.pkg.json`）才知道正确构建命令。
**对策**：先读 README / AGENTS.md / moon.pkg；不确定就 `glob` 找构建脚本。

### W5. 超长会话上下文膨胀 + 失败重试双倍浪费
某会话 196 条消息、390 万 tokens、最后 error 退出。prompt tokens 从 66K 涨到 72K，每轮都在重传巨量历史。
**对策**：任务超 ~50 条消息果断拆新会话（git 提交进度后，新会话只带 spec + git 状态）。

### W6. 反复获取同一 API 文档
某会话末尾连续 4+ 次拉取同一个 `input()` 函数签名（每次返回相同内容）。
**对策**：拿到工具结果立即用自己的话总结关键签名到代码/笔记，不要用时重查。

### W7. 含糊的任务指令容易跑偏
无明确目标的会话（如「Session 1」）会自行扩张任务范围。
**对策**：任务书写明目标、边界、验收标准；超过 1 个目标就拆会话。

### W8. 编译失败循环
6 次 build-fail、339 迭代的会话证明：**不查根因就重试是烧 token 的最快方式**。
**对策**：一次失败后先读完整错误输出（`2>&1 | tail -50` 或 `--output-json | jq`），定位根因，一次修复。

## 4. 检查清单（每次会话开始前过一遍）

- [ ] 确认 `moon version` 与构建命令（`moon build --target native --release cmd`）
- [ ] 模型选择：任务类型是执行型 → 便宜模型；复杂推理 → 才用好模型
- [ ] 是否已读相关 spec？一次并行读完
- [ ] 目标文件用 file_reader 一次读完，不用 grep 试探
- [ ] 大文档读完立即写要点到 todo
- [ ] 编译失败 → 先读完整错误再动手
- [ ] 无依赖工具调用合并为一条消息
- [ ] 任务预计超 50 条消息 → 规划拆分会话 + git 接力
