# Harness 方法论在 MBOpenClacky 项目中的应用方案

> **文档版本**: 1.0  
> **创建日期**: 2026-07-06  
> **适用项目**: MBOpenClacky（MoonBit AI Agent CLI/Web）

---

## 一、现状分析

### 1.1 项目特征与 Harness 适配度

MBOpenClacky 是一个 ~70,000 行源码、22+ 细粒度包的复杂 AI Agent 系统。以下特征决定了 Harness 方法论的高度适配性：

| 项目特征 | Harness 适配分析 |
|---------|-----------------|
| **22+ 细粒度包**（agent, client, tool, skill, mcp, channel, server, web 等） | 天然适合最小混沌单元切分——每个包就是一个可独立验证的边界 |
| **多 LLM 后端**（12 种 Provider 预设） | Provider 切换涉及大量上下文，需要 spec 锚定决策 |
| **6 个 IM 适配器**（飞书/企微/Telegram/Discord/钉钉/微信） | 适配器模式统一但细节各异，适合 codemap 导航 |
| **GEP 技能自进化系统** | 复杂系统，0→1 阶段已过，1→N 迭代需要 spec 增量 |
| **Web 前端 ~40-50% 完成度** | 大量待开发功能，适合用 Harness 流程整包推进 |
| **部署基础设施 ~30%** | 缺失 CI/CD、进程守护、日志轮转——需要 0→1 建设 |
| **~1,400+ 测试用例，全模块覆盖** | 多层 safety net 的第 2/4 层已有良好基础 |
| **MoonBit 语言（AOT 编译、强类型）** | 类型系统本身就是 safety net 的一层 |

### 1.2 当前开发流程的痛点

根据 `project-status-and-deployment-guide.md` 和 `AGENTS.md` 的分析：

1. **上下文管理困难**：22+ 包的代码地形复杂，AI 接手任务时需要大量上下文才能理解项目结构
2. **长尾差距在拉开**：头部开发者能整包交付任务，尾部还停留在逐行补全
3. **Web 前端和部署基础设施差距大**：需要大量 0→1 和 1→N 的并行推进
4. **缺少 spec 沉淀机制**：决策散落在代码注释和对话中，跨 session 接续困难
5. **无 CI/CD 流水线**：所有测试和构建依赖手动执行

### 1.3 适用场景矩阵

| 场景 | Harness 适用度 | 推荐姿态 |
|------|---------------|---------|
| Web 前端管理面板开发（8 个面板待建） | ★★★★★ | 0→1：每个面板一个任务包 |
| CI/CD 流水线建设 | ★★★★★ | 0→1：从 GitHub Actions 起步 |
| 浏览器工具完善（65-70% → 100%） | ★★★★☆ | 1→N：读 codemap + 增量 spec |
| TUI 组件增强（hook 事件、组件） | ★★★★☆ | 1→N：历史决策在 docs/ 中 |
| 新增 IM 渠道适配器 | ★★★★☆ | 0→1→N 混合：参考现有适配器 spec |
| Agent 核心逻辑修改 | ★★★☆☆ | 1→N：高频转向，边界严格 |
| 加密模块（derive_key PBKDF2） | ★★★☆☆ | 1→N：安全敏感，多层验收 |
| 日常 bug 修复 | ★★★☆☆ | 轻量 Harness：spec 增量 + checkpoint |

## 二、具体实践指南

### 2.1 Spec 体系建立

#### 目录结构

```
specs/
├── README.md                          # spec 索引和使用说明
├── _templates/
│   ├── idea-doc-template.md           # 0→1 启动 spec 模板
│   ├── task-package-template.md       # 任务包模板
│   └── incremental-spec-template.md   # 1→N 增量 spec 模板
├── active/                            # 进行中的 spec
│   ├── 2026-07-06_web-admin-panels.md
│   ├── 2026-07-06_cicd-pipeline.md
│   └── ...
├── completed/                         # 已完成的 spec（归档）
│   ├── 2026-06-30_aes-gcm-ffi.md
│   └── ...
└── decisions/                         # 架构决策记录（ADR）
    ├── ADR-001_struct-trait-over-mixin.md
    └── ...
```

#### Spec 文件命名规范

- 格式：`YYYY-MM-DD_<short-slug>.md`
- 日期为创建日期
- slug 用 kebab-case，简短描述目标
- 完成后从 `active/` 移到 `completed/`

#### Spec 维护规则

1. **No Spec, No Code**：任何超过 100 行代码改动的任务，必须先有 spec
2. **活 spec**：spec 不是一次性文档，随开发推进不断回写
3. **真相源**：当代码和 spec 冲突时，以 spec 为准（更新 spec 或修正代码）
4. **checkpoint 沉淀**：checkpoint 上的加料、追问、转向，都要回写到 spec

### 2.2 最小混沌单元定义

#### 切分原则：小到可检查，大到可自治

MBOpenClacky 的最小混沌单元按以下优先级切分：

| 切分维度 | 适用场景 | 示例 |
|---------|---------|------|
| **按包** | 改动集中在单个包内 | `lib/mcp/` 的 Stdio 挂起修复 |
| **按功能** | 跨包的功能特性 | Web 管理面板（涉及 web/ + server/ + 前端 JS） |
| **按文件** | 大文件的局部修改 | `lib/web/server.mbt` 新增路由组 |
| **按阶段** | 大功能的分步交付 | 浏览器工具：先进程启动 → 再标签管理 → 再截图 |

#### 具体切分建议

**Web 前端管理面板（8 个面板）**：每个面板 = 1 个最小混沌单元

| 任务包 | 涉及文件 | 预估行数 | 验收标准 |
|--------|---------|---------|---------|
| MCP 管理面板 | `web/js/mcp.js` + `lib/web/handlers_mcp.mbt` | ~200 + ~150 | 增删改查 MCP 服务器可用 |
| IM 渠道面板 | `web/js/channels.js` + `lib/web/handlers_channels.mbt` | ~250 + ~200 | 6 种渠道配置 CRUD 可用 |
| Cron 调度面板 | `web/js/schedules.js` + `lib/web/handlers_schedules.mbt` | ~220 + ~150 | 定时任务管理可用 |
| 备份管理面板 | `web/js/backups.js` + `lib/web/handlers_backups.mbt` | ~150 + ~100 | 备份创建/恢复/删除可用 |
| 计费面板 | `web/js/billing.js` | ~180 | 计费状态展示可用 |
| Browser 控制面板 | `web/js/browser.js` | ~180 | 浏览器状态/操作可用 |
| 回收站面板 | `web/js/trash.js` | ~120 | 文件恢复/清空可用 |
| Git 面板 | `web/js/git_panel.js` + 后端 API | ~250 + ~200 | Git 操作面板可用 |

**浏览器工具完善（65-70% → 100%）**：按功能阶段切分

| 任务包 | 涉及文件 | 验收标准 |
|--------|---------|---------|
| 高级表单交互 | `lib/tool/browser.mbt` | dblClick/drag/scroll/wait 可用 |
| 截图管道完善 | `lib/tool/browser.mbt` | 压缩/缩放/磁盘保存可用 |
| 快照两段式压缩 | `lib/tool/browser.mbt` | 大快照自动压缩到 150KB 以下 |

**CI/CD 流水线建设**：按阶段切分

| 任务包 | 内容 | 验收标准 |
|--------|------|---------|
| 基础流水线 | `moon check` + `moon build` + `moon test` | PR 自动触发，结果可见 |
| Docker 镜像构建 | 多阶段构建 + 推送 | 镜像可拉取、可运行 |
| 自动化巡检 | 安全扫描 + 依赖检查 | 报告自动生成 |

### 2.3 Checkpoint 机制实施

#### Checkpoint 触发规则

在 MBOpenClacky 中，以下节点必须触发 checkpoint：

| 触发条件 | checkpoint 内容 |
|---------|----------------|
| **准备改代码前** | 复述 diff 计划：改哪些文件、为什么、风险是什么 |
| **引入新依赖前** | 说明依赖名称、用途、许可证、替代方案 |
| **跨包改动时** | 列出所有受影响的包和 `pkg.generated.mbti` 变更 |
| **涉及安全相关代码** | 加密、认证、权限相关改动必须 checkpoint |
| **完成一个任务包后** | 验收报告：改了什么、跑了什么验证、结果是什么 |

#### Checkpoint 上的 6 种动作（MBOpenClacky 版）

| 动作 | 触发条件 | 示例输入 |
|------|---------|---------|
| **放行** | 计划合理、风险可控 | `do it` / `继续` / `ok` |
| **加料** | 沿当前方向补约束 | `注意保持与现有 channel adapter 的接口一致` |
| **追问** | 需要澄清不确定性 | `为什么用这个数据结构？有没有考虑过 MoonBit 的 trait？` |
| **绕道** | 模型方案偏离目标但可挽救 | `回到本轮目标——不要重构现有 API` |
| **回炉** | 当前路径走不通 | `这条路走不通了，回到 spec 的'明确不做'那一节重读` |
| **阻止** | 发现严重问题 | 直接 ctrl-c 中断 |

#### Checkpoint 的副作用：对抗上下文腐烂

每次 checkpoint 上让模型复述：
1. 当前任务包的目标是什么
2. 已经完成了什么
3. 下一步准备做什么
4. 有什么风险

这个复述动作把目标拉回模型的近期上下文，利用 recency bias 对抗 lost-in-the-middle。

### 2.4 多层 Safety Net 与现有流程结合

MBOpenClacky 已有良好的测试基础（1,400+ 用例、全模块覆盖），以下是多层 safety net 的具体落地：

```
第 5 层 · 灰度 + 金丝雀 + 一键回滚（线上兜底）
    ↑ 风险越高越需要：Web 服务部署、IM 渠道消息处理
    │
第 4 层 · CI/CD 自动化回归 + 巡检
    ↑ moon check + moon build + moon test + Docker 构建
    │  ← 当前缺失，需要建设（§3 阶段 2）
    │
第 3 层 · 他测（独立视角 review）
    ↑ 让另一个 AI agent 做 code review
    │  ← 可用 open-code-review skill 或 CodeReview subagent
    │
第 2 层 · 自测（模型自己跑测试）
    ↑ moon test lib/xxx --filter "xxx*"
    │  ← 已有 1,400+ 用例基础
    │
第 1 层 · 自验（模型写验收报告）
    ↑ 改了什么 / 跑了什么 / 结果 / 验收对照 / 未覆盖 / 排查建议
```

#### 各层具体实施方式

**第 1 层 · 自验**：每个任务包完成后，模型生成验收报告

```markdown
## 验收报告：<任务包名称>

### 改了什么
- 新建/修改了哪些文件（diff 摘要）

### 跑了什么验证
- moon check → 结果
- moon test lib/xxx → 结果
- 手动验证命令 → 输出

### 验收标准对照
- [x] 标准 1
- [x] 标准 2
- [ ] 标准 3（原因：...）

### 没覆盖的
- 待后续补充的功能

### 后续排查建议
- 如果出问题，从哪里排查
```

**第 2 层 · 自测**：利用现有 `moon test` 基础设施

```bash
# 全量类型检查（每次 checkpoint 必跑）
moon check

# 目标包测试（任务包验收必跑）
moon test lib/<package>

# 带 filter 的精确测试
moon test lib/agent --filter "session*"

# 格式化检查
moon fmt --check
```

**第 3 层 · 他测**：独立视角 review

- 使用 `open-code-review` skill 对 git diff 做 review
- 或使用 CodeReview subagent 做独立审查
- 关键模块（agent, client, tool, mcp）改动必须他测

**第 4 层 · CI/CD**：自动化回归（待建设）

```yaml
# .github/workflows/ci.yml 核心流程
moon check                          # 类型检查
moon build --target native --release cmd  # 构建
moon test                           # 全量测试
docker build -t mbopenclacky:ci .   # Docker 构建
```

**第 5 层 · 灰度 + 金丝雀**：线上风险控制

- Web 服务部署：使用 feature flag 控制新功能
- IM 渠道消息处理：新适配器先在测试群验证
- 配置变更：灰度 key 控制，出问题一键回滚

#### 风险等级与启用层数

| 改动风险 | 启用层数 | 示例 |
|---------|---------|------|
| 低风险 | 1-2 层 | 文档修改、注释更新、格式化 |
| 中风险 | 2-3 层 | 单包功能增强、新工具实现 |
| 高风险 | 3-4 层 | 跨包改动、Agent 核心逻辑、加密模块 |
| 极高风险 | 4-5 层 | 线上服务部署、IM 渠道消息处理、权限变更 |

### 4.2 Spec 模板

#### 0→1 启动 Spec 模板（`specs/_templates/idea-doc-template.md`）

```markdown
# <项目名称> · 启动 Spec (IDEA_DOC)

> **创建日期**: YYYY-MM-DD
> **状态**: 讨论中 / 实施中 / 已完成
> **负责人**: <名字>

## 核心目标
<一段话说清楚要做什么>

## 关键能力
- 能力 1
- 能力 2
```

## 六、总结

Harness 方法论在 MBOpenClacky 项目中的核心应用原则：

1. **No Spec, No Code**：超过 100 行改动的任务，先写 spec 再动手
2. **最小混沌单元**：按包/功能/阶段切分，小到可检查、大到可自治
3. **水流理论**：不规定模型每一步怎么写，用边界 + checkpoint + 安全通道控盘
4. **上下文三件套**：spec 持久化决策、codemap 摘要地形、new-chat 对抗腐烂
5. **多层 Safety Net**：自验 → 自测 → 他测 → CI/CD → 灰度，风险越高启用越多层
6. **checkpoint 沉淀**：协作中发现的东西，最终回到 spec 和 codemap 里

> 未来真正稀缺的，不是写代码的人，而是能让大模型在正确边界里大胆流动，并且把端到端结果安全收回来的人。
