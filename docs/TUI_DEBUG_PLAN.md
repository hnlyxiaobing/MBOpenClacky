# MBOpenClacky TUI 迭代调试循环 (Debug-Refine Loop) 第1轮分析

## 1. 本质差异分析（第一性原理）

通过对比源项目（openclacky）的截图和当前项目（MBOpenClacky）的截图，可以发现两者在 TUI 架构上的**第一性原理级差异**：
- **源项目（openclacky）**：采用的是 **Inline TUI (滚动式命令行界面)** 架构。历史对话内容直接输出到标准输出，依赖终端自带的滚动缓冲区（Scrollback Buffer）；底部通过 ANSI 控制码动态渲染一个固定或浮动的输入框与下拉提示菜单。
- **当前项目（MBOpenClacky）**：引入了 `onebit-tui` 和 `onebit-yoga` 库，这属于 **Retained-mode Full-screen TUI (全屏保留模式界面)** 架构。它通过进入备用缓冲区（Alternate Screen），接管整个终端屏幕的绘制权，每帧重新计算布局树并从 `(0,0)` 坐标开始全屏绘制。

此外，截图2中出现的文字堆叠（如 `stimated)00t yetP%P%P%P%...` 和乱入的 `Submit` / `Quit` 按钮）暴露了当前系统在**布局计算 (Layout Engine)** 与**渲染管线 (Render Pipeline)** 的严重失控。

## 2. 根因定位

1. **根节点约束缺失导致 Flex 坍塌**：
   在 `lib/tui/tui.mbt` 的 `build_main_layout` 函数中，组装的根视图仅仅是 `@view.View::container_views([...]).direction(Column)`。
   - 核心问题：在 Yoga 布局引擎中，如果根节点没有显式设置宽度和高度为 100%（或具体的终端行/列数），其默认表现为 `Auto`（包裹内容）。
   - 后果：被标记为 `.flex(1.0)` 的主内容区域（对话列表）因为父节点没有确定的高度而无法扩展，高度坍塌为 0。于是，所有的子组件（状态栏、输入框、按钮、工具输出占位符等）互相失去 Y 轴偏移量的参照，最终全部叠加在终端左上角 `(0,0)`，造成了混乱的字符交叠。

2. **渲染字符串的安全转换或终端清屏异常**：
   重叠现象叠加 `onebit-tui` 的 FFI C 语言渲染调用后，覆盖打印的字符串（如包含颜色的 ANSI 控制序列）可能没有正确对齐终端格子，甚至暴露出原始内存残影或错误的转义码，形成截图里的“乱码”。

## 3. 第一轮整体解决方案与计划

由于当前项目代码结构已深度绑定 `onebit-tui` 的响应式组件架构，简单地放弃该框架重写内联控制并不现实。我们的方案是**修复全屏布局体系，并在视觉层面上实现对源项目的“像素级”伪装（包括底部对齐的输入框、占据剩余空间的对话滚动区和隐藏明显边框的样式）**。

### 第一轮执行计划：

1. **修复根节点约束**：
   修改 `lib/tui/tui.mbt` 中的 `build_main_layout`，通过 `@ffi.get_terminal_size()` 获取 `terminal_width` 和 `terminal_height`，并使用 `.width()` 和 `.height()` 将这些绝对数值传递给根 `Column`，强制撑开全屏，激活 Yoga 的 Flex 特性。
2. **清理顶部错乱的占位组件**：
   排查 `input_bar.mbt` 和 `status_bar.mbt` 中内部元素的尺寸问题，确保 `.direction(Row)` 的组件拥有明确的 `.height()` （例如固定的单行高度 `1.0` 或 `3.0`），防止子元素在纵向上的计算混乱。
3. **消除乱码与重叠**：
   在正确的 Flex 布局下，UI 应该会正常上下分布。如果仍然存在乱码，需要排查 FFI 中的 Clear Screen 调用是否正常工作。

## 4. 验证与迭代机制
执行上述代码修改后，我将通过 `moon check` 确保代码正常编译。由于 TUI 需要真实终端进行渲染，我无法直接截图，但我会通过审查修改后的布局逻辑是否能逻辑上推导出正确的三段式（顶/中弹性/底）排版。如果发现终端无法拉伸或者 `onebit-tui` 缺乏百分比布局的支持，我将进入第二轮循环，寻找硬编码终端尺寸变动事件的回调机制来保证布局强约束。
