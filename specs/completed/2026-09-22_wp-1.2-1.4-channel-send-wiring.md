## 问题描述 [必填]

四个未接通渠道（飞书/企微/钉钉/微信）中，飞书已由 WP-1.1 接通；钉钉、企业微信、微信三条通道的发送侧仍是诚实 stub 或存在未接线的方法：

1. **钉钉**：发送侧（webhook / robot API）本身已是真实实现，但 `DingTalkApiClient::open_stream_connection` 与 `download_file_url` 返回 `not yet wired to HTTP transport`，且 `DingTalkAdapter::start`/`stop` 留有误导性 TODO（会让读者以为接收侧整体未实现）。
2. **企业微信**：`WeComAdapter::send_text` 直接 `Err("WeCom send_text is not implemented yet")`；`start` 的注释宣称 send/receive 均未实现。
3. **微信**：`WeixinAdapter::send_text` 直接 `Err("Weixin send_text is not implemented yet")`；`weixin_aes_encrypt`/`weixin_aes_decrypt` 为 placeholder（返回 "requires moonbitlang/x/crypto"），AES-128-ECB 原语缺失是计划中登记的贵模型 FFI 环节（WP-1.4a）。

三条渠道的接收侧（`ChannelManager::handle_webhook` → `parse_event`）在 stubfix-01 已挂载，本次不动。

### 详细分析

**钉钉的真实缺口是"两个 API 方法 + 两处误导注释"**，而非发送链路：`send_text` 的三级策略（sessionWebhook 缓存 → robot API → 配置 webhook）本来就调用真实 HTTP。因此 WP-1.2 的实质是把 `open_stream_connection`/`download_file_url` 接成真调用，并消除"接收整体未实现"的错误印象。

**企微存在两条并存的协议痕迹**：`wecom_ws.mbt` 是 aibot WebSocket 协议（`aibot_subscribe`/`aibot_send_msg` + 帧构建器），而 `WECOM_API_BASE` 是 cgi-bin REST。计划明确"access_token 获取 + 缓存；`message/send` 接线；WebSocket 收发用 `@async.websocket`"——即发送走 REST、WS 留给接收侧。本次按计划只接 REST 发送，WS 帧构建器与状态机原样保留（它们是接收侧资产，已有测试覆盖）。

**微信 AES 的模式判断**：`build_weixin_aes_key` 把配置值当作 32 个 hex 字符（16 字节密钥），与 AES-128 的密钥长度一致；ECB 模式不需要 IV（原实现返回的 `iv_hex` 仅保持 API 兼容）。由于 ECB 原语不做填充，需自实现 PKCS#7：媒体文件长度不保证是 16 的倍数。

**测试策略的复用点**：WP-1.1 已在 `feishu_mock_wbtest.mbt` 建立 raw TCP mock server 与请求体读取（含 chunked）原语；本 spec 将其中三个与飞书无关的辅助函数改名为通用名复用，避免在三个新渠道的测试里重复 60 行管道代码。

## 决策 [必填 - 含为什么]

1. **决策 1（钉钉接线范围）**：只把 `open_stream_connection` 与 `download_file_url` 接成真实 HTTP POST + 响应解析（缺 `endpoint`/`downloadUrl` 即报错）；`start`/`stop` 的 TODO 改为如实描述，不在本 WP 内实现 Stream Mode WS 循环。
   - **为什么**：计划对 WP-1.2 的触点正是这两处 `not yet wired`；WS 接收循环需要长连接生命周期与重连策略，属独立工作包。把 TODO 改写成事实（接收走 webhook 路由）比保留误导性 TODO 诚实，也与 WP-1.1 对 `start()` 的处理一致。
2. **决策 2（企业微信客户端形态）**：新建 `lib/channel/wecom_api.mbt` 的 `WeComApiClient`（持自己的 `TokenCache`），`WeComAdapter` 用 `api_client` 字段替换从未被读取的 `access_token_cache` 字段。
   - **为什么**：与 feishu/dingtalk/weixin 的 `*_api.mbt` 分层一致；token 缓存必须跨多次发送存活（每次发送新建 client 会导致每发必取 token）。原 `access_token_cache` 是死状态，删除而非保留两个缓存。
3. **决策 3（企业微信 chat_id 映射）**：`send_text` 的 `chat_id` 映射为 REST 的 `touser`；群聊投递（`appchat/send`）不猜测实现，由平台返回的 `errcode` 如实报错。
   - **为什么**：适配器的 `chat_id` 语义在不同平台不同，企微群 id 与 userid 无法从字符串可靠区分（现有 `detect_wecom_chat_type` 用的是 `@` 启发式，不足以决定端点）；猜错的端点会得到更难诊断的错误。
4. **决策 4（AES 由 x/crypto 承载）**：导入 `moonbitlang/x/crypto`，用 `aes_ecb_encrypt/decrypt` + 自实现 `pkcs7_pad`/`pkcs7_unpad`；额外暴露无填充的 `weixin_aes_ecb_encrypt/decrypt` 以便对官方向量。
   - **为什么**：计划把"若 x/crypto 无 ECB 则评估 FFI"列为贵模型环节；验证记录表明 ECB 已在包内，FFI 评估可直接取消。FIPS-197 向量是 16 字节块级输入，必须走无填充路径才能对齐，故两层都暴露。
5. **决策 5（微信发送前置处理）**：`send_text` 先 `sanitize_for_weixin`（微信不渲染 Markdown），附 `context_token`（无则空串），`ret != 0` 报错并对 `-2` 标注限流；缺 `uin`（无法构造 client）时如实报 `no api_client`。
   - **为什么**：sanitize 与限流处理是本仓既有资产（`sanitize_for_weixin`/`is_rate_limited`），不用则发送会把 Markdown 原样推给用户、把限流当成功。
6. **决策 6（业务错误码检查）**：企微 `check_wecom_errcode` 对所有响应要求 `errcode == 0`（缺字段也视为失败）；微信 `ret != 0` 即失败；钉钉沿用 HTTP 状态检查。
   - **为什么**：三家语义不同（企微/微信 HTTP 200 + 业务码，钉钉 HTTP 状态），但共同点是"不检查就是静默假成功"，违反诚实纪律。
7. **决策 7（测试策略）**：新增一个通用 mock TCP server（按路径路由，单实例覆盖三渠道），配合 `api_base` 注入跑真 HTTP 往返；AES 走纯函数向量与边界用例；两条锁定 stub 行为的旧测试改为真实错误契约。
   - **为什么**：DoD 继承 WP-1.1 的"HTTP 路径经本地 mock 跑通一次"；`api_base` 注入是唯一能让适配器在不触公网的前提下被端到端测到的口子。
8. **决策 8（mock 管道复用而非复制）**：把 `feishu_mock_wbtest.mbt` 的 `mock_feishu_send`/`mock_feishu_read_body`/`mock_feishu_parse_hex` 改名为 `mock_http_*` 并注明共享。
   - **为什么**：三者与飞书无关；不改名而复制会在测试层留下 60 行重复的 chunked 读取逻辑。改名是机械操作，不改行为（该文件的飞书测试同步更新）。
