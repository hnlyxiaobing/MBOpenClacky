## 问题描述 [必填]

`README.md`/`CLAUDE.md` 把「GEP 技能自进化（EvolutionEngine + SkillReflector + AutoCreator）」列为核心技术优势，但**反思（Reflect：执行后改进技能）这一步是空壳**，且 Web 侧两个进化端点是**硬编码假成功**（返回固定 JSON，不读任何真实状态），违反项目「不得静默假成功」的诚实纪律。

具体缺口：

1. `SkillReflector::apply_improvements` 是 placeholder——返回 `"... (placeholder)"` 字符串，不做任何改进。其上游 `EvolutionEngine::handle_post_execution`（`lib/skill/evolution.mbt:97`）因此永远只产出占位文本。
2. `POST /api/skills/:name/evolve`（`lib/web/handlers_skills.mbt:643`）返回硬编码 `{"evolution_id":"evo-001","status":"evolving"}`——**假成功**；`name` 参数被 `ignore()`。
3. `GET /api/skills/evolution/history`（`lib/web/handlers_skills.mbt:657`）返回硬编码 `{"history":[],"total":0}`——**假成功**。
4. **不存在进化日志持久化**：全仓无 `evolution_log`/`EvolutionLog` 任何符号，反思产出无处落盘。
5. 上述两端点**无任何前端调用方**（`web/features/skills/` 内无 `evolve`/`evolution` 命中），属"死端点 + 假成功"叠加。

### 详细分析

GEP 三段式里 **AutoCreator 与 EvolutionEngine 骨架在位**，缺的是中间那段「反思 → 改进」。已验证：

- **纯函数、无网络的部分已经真实**：`SkillReflector::reflect`（评分）与 `AutoCreator`（模式检测，`lib/skill/auto_creator.mbt`，8KB 实现 + wbtest）。
- **断点在 IO/网络边界**：`apply_improvements` 需要（a）LLM 产出结构化建议、（b）落盘、（c）可选回写技能文件——三件都是 IO，而 `lib/skill` 刻意不依赖 `@client`。
- **Web 端点是"死端点 + 假成功"**：既无真实实现，也无调用方（与 WP-1.7 修掉的 `/channel-manager doctor` 端点同型：声明存在、无人调用、返回不可信结果）。

因此本 WP 的性质是**接线**（roadmap §2.2 建议动作），不是降级声明。

## 决策 [必填 - 含为什么]

1. **决策 1：LLM 调用落在 Web handler 层，`lib/skill` 保持纯净（不加 `@client`）。**
   为什么：`lib/skill/moon.pkg` 现无任何网络依赖，`reflect`/`AutoCreator` 因此可在无网络的 wbtest 里直接单测；把 `@client` 塞进库层会把网络依赖扩散到全部下游，并可能引入依赖环。`lib/web` 已同时依赖 `@client` 与 `@skill`，是天然接线点（同 WP-1.5 把媒体网络调用放 handler 层、`lib/media` 只管构建/解析的做法）。

2. **决策 2：反思证据（transcript）由调用方提供且必填；缺失即 400，不伪造证据。**
   为什么：已 grep 确认全仓**不存在技能↔执行记录**（无 `skill_usage`/`SkillExecution` 等），运行期拿不到"某技能上次执行的结果"。若缺证据就编一个（例如拿 SKILL.md 原文当执行结果）会得出无意义评分——正是项目禁止的假成功。故 `transcript` 必填，缺失时返回可诊断 400 并说明如何提供。

3. **决策 3：回写 SKILL.md 是显式 opt-in（`apply: true`），且**总是**先写时间戳备份。**
   为什么：用户已确认要「建议 + 自动改写 SKILL.md」，但静默覆盖用户技能文件是不可逆破坏。设计为：默认只产出建议（不写文件）；`apply:true` 时才回写，并在回写前把当前 `SKILL.md` 复制为 `SKILL.md.bak.<unix_ts>`，响应回报 `applied`/`backup_path`。既给了"自动改写"能力，又不丢原有内容。

4. **决策 4：进化日志落在 `~/.mbopenclacky/skills/evolution_log.json`，JSON 数组、最新在前、上限 500 条。**
   为什么：与技能资产同域（`@utils.skills_dir()`），便于用户自查与迁移；结构用 JSON 数组而非 JSONL，因为 `x/fs` 无 rename、也无可靠 append 原语（已验证），读-改-写数组最简单可测；设上限避免无界增长。写入走 `@fs.write_string_to_file`（与既有 `write_skill_content` 一致）。**注意**：因无 rename，写入非原子，规格如实说明这一限制而不假装原子。

5. **决策 5：删除占位 API `apply_improvements`，替换为三个纯函数 + 一个 IO 函数。**
   为什么：保留一个返回占位文本的 pub API 等于保留谎言（且台账 3 行不会消失）。替换为：
   - `build_reflection_prompt(report, skill_content, transcript) -> String`（纯，可测）
   - `parse_reflection_response(text) -> Result[ReflectionProposal, String]`（纯，容错解析，含代码围栏剥离）
   - `ReflectionProposal::{suggestions, revised_skill_md}`（新类型）
   - `apply_proposal(skill_dir, proposal) -> Result[String, String]`（IO：备份 + 回写，返回 backup_path）
   为什么这几个：Prompt 构建与响应解析是反思的核心智力产物且**可离线用固定字符串测**（满足 DoD「有 wbtest」），把不可测的网络留给 handler。

6. **决策 6：本 WP 不新增面板 UI。**
   为什么：面板无任何技能执行证据可提交（决策 2），若加"优化"按钮就只能提交空证据或伪造证据，反而制造新的假成功；且方案 DoD 只要求"反思产出可持久化并**可被 Web 查询**"，查询端点返回真实数据即达标。面板展示进化历史需新增 i18n 键 + 渲染 + CSS，属独立 UI 任务，**明确列为范围外**并在台账登记（避免成为下一轮的隐性缺口）。

7. **决策 7：`EvolutionEngine` 形状不变，`handle_post_execution` 改为产出报告而非调用空壳。**
   为什么：`EvolutionAction` 是 pub enum（`Created`/`Improved`/`NoChange`），改枚举会破坏下游穷尽匹配与既有 wbtest；改法是 `handle_post_execution` 在 `should_improve` 时以 `Improved` + 拼接后的 suggestions 作为 `diff_summary` 返回，把"调 LLM + 回写"交给 handler。
   **实施期修正（2026-09-22）**：handler **未**改为经由 `EvolutionEngine::evolve(PostExecution(...))`。原因是响应与日志都需要完整 `ReflectionReport`（分数、suggestions 数组），而 `EvolutionResult` 只携带 `action`/`skill_name`/`diff_summary`；加字段会破坏既有的 `EvolutionResult` 结构体字面量与 derive。权衡后由 handler 直接调用 `SkillReflector::reflect`（同一纯函数，无重复计算），`EvolutionEngine` 保持纯引擎角色。**如实说明**：因此引擎的 PostExecution 分支的运行期调用方仍只有 wbtest；把引擎接入 agent 运行期需要先建"技能执行台账"机制，已列为范围外独立 WP（见"依赖关系"）。此处按项目诚实纪律记录差异，不虚构"引擎已获运行期调用方"。

## 风险评估 [必填]

| 风险 | 影响 | 缓解方案 |
|------|------|---------|
| LLM 返回非严格 JSON（围栏/前后缀/多段） | 中 | `parse_reflection_response` 容错解析 + 畸形输入单测；解析失败记日志 `error` 并返回可诊断错误，不回写文件 |
