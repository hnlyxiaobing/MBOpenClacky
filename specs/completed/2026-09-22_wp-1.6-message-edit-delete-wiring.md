## 问题描述 [必填]

P2 渠道补齐项：**编辑/撤回**能力声明与实现不一致，且撤回不在接口内。

1. **Telegram**：`update_message` 是诚实 stub（`Err("Telegram update_message is not implemented yet")`），但 `supports_message_updates` 返回 `true`（注释称支持 `editMessageText`）——Bot API 确可编辑，属可接线却被留成 stub。
2. **Discord**：`DiscordApiClient` 的 `edit_message`/`delete_message`/`get_current_user`/`upload_file` 四方法为 stub，`download_attachment` 更糟——**不发任何 HTTP 却返回 `Ok("")`（静默假成功）**，另有一处 `TODO: Execute async HTTP GET via @http`；而 `DiscordAdapter::supports_message_updates` 同样返回 `true`。Discord 的 PATCH/DELETE 端点真实存在。
3. **撤回不在接口里**：`Adapter` trait 只有 `send_text`/`update_message`/`supports_message_updates`/`validate_config`，`delete_message` 无位置，因此"撤回"需要先扩接口（含 `AnyAdapter` 分发与各平台实现）。
4. **非缺口**：企微/微信/钉钉 `supports_message_updates=false` 并如实报"不支持编辑"，是平台能力事实，本 WP 不改变该判定（仅补撤回侧的同类如实声明）。飞书 `update_message` 已由 WP-1.1 接通（`PATCH` + code 检查），本 WP 无需重做。

### 详细分析

**目标是消除"声明与实现不一致"而非新增平台能力**：Telegram `editMessageText`/`deleteMessage`、Discord `PATCH`/`DELETE /channels/{id}/messages/{id}`、飞书 `DELETE /im/v1/messages/{message_id}` 都是各平台公开且稳定的端点，HTTP 基础设施（`http_post_json`/`http_patch_json`/`http_get_json`、`@client` 异步传输、mock TCP 测试基建）在 WP-1.1~1.5 已全部具备。因此路线图 §1.2 的"接线 vs 降级声明"二选一，按 D-A/D-B 已放行的 A 路线选择**接线**，而不是把 `supports_message_updates` 改回 `false`。

**撤回语义需要接口扩展**：`delete_message` 必须在 `Adapter` trait 内才有统一调用点（`AnyAdapter` 分发是 web/manager 层的唯一多态入口）。同时撤回也需要一个与 `supports_message_updates` 对称的能力声明，否则"企微/微信/钉钉不支持撤回"这一事实无处如实暴露，会重演本 WP 要修的那类不一致。

**一处静默假成功**：`download_attachment` 返回 `Ok("")` 且从不发 HTTP，属 stubfix-02 明令禁止的模式，且台账以 `TODO` 命中记录在案；本 WP 必须一并消除（改为真实 GET 取 body）。

**`start()` 是非 async 的约束**：`Adapter::start` 签名不含 `async`，`DiscordAdapter::start` 原先在同步路径里调用 `get_current_user()`（因此对方必须同步——这正是它保留 stub 的隐性原因）。接线为真实异步方法后，`start()` 不能再调用它；而 `bot_user_id` 全仓无读取方，故删除该同步探测，把真实方法交给异步的 web 连通性探针使用。

## 决策 [必填 - 含为什么]

1. **决策 1（选择接线，不降级标志）**：把 Telegram/Discord 的编辑/撤回接到真实 HTTP 端点，保留 `supports_message_updates=true`。
   - **为什么**：D-A/D-B 已放行 A（接线路线）；端点真实存在且基础设施齐备，降级标志会让"已宣传的能力"永久停在 stub，且违背路线图"把已宣传的能力做实"的结论。
2. **决策 2（扩 trait 两个方法）**：`Adapter` 新增 `async fn delete_message(Self, String, String) -> Result[Unit, ChannelError]` 与 `fn supports_message_deletion(Self) -> Bool`，`AnyAdapter` 同步补 extend 列表与 6 平台分发。
   - **为什么**：撤回要经 `AnyAdapter` 统一调用；能力声明与 `supports_message_updates` 对称，才能让"平台不支持撤回"如实暴露而不是靠调用方猜。
3. **决策 3（DELETE 传输走 `lib/client` 包装）**：`lib/client/platform_http.mbt` 新增 `http_delete(url, headers, timeout_ms)`（`send_request(Delete, url, "", …)`）；`lib/channel/http_helper.mbt` 新增 `http_delete_ok`（只看状态，Discord 204 无 body）与 `http_delete_json`（飞书 200 + code 检查）。
   - **为什么**：`HttpMethod` 是 `pub enum` 且既有注释明示外部只能经包装函数构造方法，加包装与 `http_post/get/patch` 先例一致；204 空 body 若强行走 JSON 解析会假报失败，故按响应形态分两个助手。
4. **决策 4（`download_attachment` 改真实 GET）**：新增 `http_get_text`，`download_attachment` 返回真实响应体，删除 `Ok("")` 与 `TODO`。
   - **为什么**：`Ok("")` 是静默假成功（stubfix-02 的禁止模式），台账已按 TODO 命中登记，接线即消除。
5. **决策 5（upload_file 走手工 multipart + `http_post_json`）**：新增 `DISCORD_UPLOAD_BOUNDARY` 与 `build_discord_upload_body`（`payload_json` 段 + `files[0]` 段），响应仍按 JSON 解析。
   - **为什么**：与飞书/媒体侧既有手工 multipart 先例同构；`http_post_json` 只负责"POST 原始 body + 解析 JSON 响应"，不强制 Content-Type，可直接复用，无需新增 bytes 传输。
6. **决策 6（Telegram 编辑不带 parse_mode）**：`build_telegram_edit_request` 去掉写死的 `parse_mode: "Markdown"`，两处相关断言同步改为"无 parse_mode"。
   - **为什么**：发送侧已有明确决策"首版纯文本发送（不带 parse_mode），富文本格式化列 backlog"（`specs/completed/2026-08-21_stubfix-06-telegram-send.md` R3）。编辑路径若带 Markdown，模型/用户文本里的 `_`/`*` 会触发 400（entity 解析失败），与发送侧行为割裂；该 builder 此前从未被生产代码调用，改动无兼容负担。
7. **决策 7（不支持撤回的平台如实报错）**：企微/微信/钉钉补 `supports_message_deletion=false` + `Err("... does not support message deletion")`，与既有编辑侧声明同构。
   - **为什么**：这三个平台本 WP 不新造撤回 API（不虚报能力），但要给统一调用点一个诚实的失败面，而不是 `Ok(())` 假成功。
8. **决策 8（`get_current_user` 的调用点迁移）**：删除 `DiscordAdapter::start` 里的同步探测（`Adapter::start` 非 async，且 `bot_user_id` 无读取方），改由 `lib/web/handlers_channels.mbt` 的 Discord 连通性探针调用真实方法（该探针此前正是为绕开 stub 而手工拼 URL）。
   - **为什么**：不引入"同步路径里启动异步任务"的复杂度；探针是异步上下文，且换成真实方法后消除了"探针与客户端两条并行实现"的重复。
9. **决策 9（测试策略）**：扩展现有 mock TCP 基建（`MockPlatformServer`/`MockFeishuServer`）做 Telegram/Discord/飞书的编辑、撤回、取用户、上传、下载真 HTTP 往返；把 4 个 discord stub 测试与 1 个 telegram stub 测试改写为"未接线端口必真报错"的闭环闸门；补 `supports_message_deletion` 声明与实现的对照测试。
   - **为什么**：DoD 要求"编辑/撤回在各已接通平台可用并有 wbtest"；无真实凭据，mock 是最高保真验证；改写而非删除存量闸门，保住 stubfix-02 的"禁止假成功"契约。
