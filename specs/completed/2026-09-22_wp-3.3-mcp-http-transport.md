## 问题描述 [必填]

MCP 只有 Stdio 传输可用：`HttpTransport` 的三个 I/O 入口（`start`/`send_message`/`send_request`）都是 `Err("HTTP MCP transport not implemented yet")`。任何以 `url` 配置的远程 MCP server（Streamable HTTP 是 MCP 的主流部署形态）在 `initialize` 阶段即失败，`lib/mcp/registry.mbt` 与 Web 面板的 MCP server 管理对 `Http` 类型形同虚设。

`README.md:41/167` 如实标注了该限制——**因此这是已披露的能力缺口，不是可信度问题**，但没有传输就无法使用远程 server。

### 详细分析

**为什么必须实现 Streamable HTTP 的两种应答形态**：MCP 规范允许服务端对同一 POST 返回 `application/json`（单帧）或 `text/event-stream`（SSE 流）。只实现一种会让一半服务端不可用，且失败面是"能连上但拿不到结果"，比直接报错更难诊断。

**为什么 SSE 要逐帧读并在命中自己的 id 时立刻返回**：服务端可以保持 SSE 流打开以推送后续消息（通知、服务端发起的请求）。若先 `read_all()` 再解析，客户端会**等一条不会关闭的流**直到超时——即使回复早已到达。逐帧 + 命中即停既避免挂死，也顺带把非本请求的帧按协议转交给 message handler（与 stdio 的 `dispatch_line` 同语义）。

**为什么要每请求新建连接**：命中回复即停止读流会让该连接处于"未读完"状态，无法复用。MCP 的工具调用频率下，每请求一次 TCP 握手是可接受的代价，换来的是不会因半读连接产生难以复现的状态 bug。

**为什么 `start` 不建连**：Streamable HTTP 无长连接；`start` 若做一次探活，会把"配置可用"和"服务端当下可达"混为一谈（后者随时会变），并使 `McpClient::initialize` 的错误来源变得难辨。保持"校验配置 + 置为可用"，把可达性交给第一个真实请求如实报错，符合"不假装成功"的既有纪律。

## 决策 [必填 - 含为什么]

1. **决策 1（`start` = 配置校验，不建连）**：校验 url 是绝对 http(s) 且有 host，通过则 `is_alive = true`。
   - **为什么**：见现状分析。`McpClient::initialize` 的 `start` 失败语义保留给"配置/平台问题"，网络问题由请求报错。
2. **决策 2（每请求一条连接）**：`send_request` 内 `@http.Client(origin)` → POST → 读应答 → `client.close()`（`defer`）。
   - **为什么**：命中即停读会让连接不可复用；避免半读连接的状态泄漏。
3. **决策 3（按 `Content-Type` 分流两种应答）**：含 `text/event-stream` 走 SSE 逐帧；否则按 JSON 取匹配帧（支持 batch 数组）。
   - **为什么**：MCP 规范两种都合法；只做一种会把另一半服务端变成"连上但没结果"。
4. **决策 4（id 严格相关 + 其余帧转交）**：复用 `parse_jsonrpc_response` 判定 id；命中前遇到的 JSON-RPC 帧转 `message_handler`，与 stdio 同语义。
   - **为什么**：request/response 必须严格相关（错误的回复比没有回复更危险）；通知与服务端请求不能丢。
5. **决策 5（会话 id 捕获与回带）**：从响应头取 `Mcp-Session-Id`（大小写不敏感，经 `Headers` 的 `CaseInsensitiveString`），后续请求经 `build_headers` 回带。
   - **为什么**：Streamable HTTP 的会话态就靠这个头；不回带会让有状态服务端把后续请求当作新会话。
6. **决策 6（通知按 202/空体为成功，≥400 与 error 对象都报错）**：`send_message` 只认"无错误"为成功。
   - **为什么**：stubfix-02 的禁止假成功：通知同样不能把服务端拒绝当成发送成功。
7. **决策 7（测试用同进程真实 HTTP 服务器）**：`@http.Server` 绑定 `127.0.0.1:0`，13 条测试全部走真实 socket（含 SSE 与拒连）；不用桩替代 socket 层。
   - **为什么**：本 WP 交付的就是 I/O；mock 掉 socket 等于不验证交付物。本地回环不触外网，CI 可用。
8. **决策 8（`wbtest` 专用依赖走 `import ... for "wbtest"`）**：`@socket`/`@io` 仅供白盒测试用来起 mock server。
   - **为什么**：产品代码不需要它们，加进产品 import 会把测试基建混入交付面；本仓此前无 `for "wbtest"` 先例，按 moon 现行语法（`.mooncakes` 内多处先例）引入。
9. **决策 9（分片验证而非整体跑包）**：Windows 本机 `lib/mcp` 全量仍挂死在 stdio python3 集成测试（WP-3.5），故按 `--filter` 分片跑本 WP 相关用例并如实标注该限制。
   - **为什么**：不能声明"包全量绿"——那是假的；分片覆盖 + 明写不可测范围才是诚实交付。
