## 问题描述 [必填]

参考机 `~/.mbopenclacky/sessions/` 下有 **32 个 `.json` 会话文件，`--list` 曾只列出 1 个**。

`list_sessions()` 对解析失败的文件 `continue`（静默跳过），`cmd inspect` 对同一文件只报"不是会话文件 + 原因"，用户看不到任何时间线。执行计划把成因笼统写为"旧 `tool_calls` schema 不匹配与文件根本不是 JSON"；本 WP 开工时逐文件核对，确认是**两类彼此独立的成因**，且第二类的覆盖面远大于预期。

### 详细分析

**两类成因必须分开处理**：

1. **整份文件不是 JSON**：早期构建把 `json.to_repr()` 写进了 `.json`。这类只能"修复性投影"——把 repr 还原成 `Json` 再走既有解码。repr 的正文是**未转义原文**，因此 `String(...)` 的终结括号必须按结构判定（体内括号成对；`String(` 之后内容里的裸 `)` 属正文），且**必须整份解析到结尾才算成功**——否则宁可报"不可读"，也不能产出半截错内容。
2. **JSON 合法但字段被多包了一层**：旧 Option 序列化器把 `Some(x)` 写成 `[x]`。这在会话级已有先例（`opt_string_field` 注释明写"previous broken Option serializer"），但消息级从未容忍——`tool_calls` 因此直接抛错，标量字段则**静默变 `None`**。

**为什么必须修第 2 类的标量字段**：`tool_call_id` 是 tool_use/tool_result 配对的唯一凭据。只修 `tool_calls` 让文件"能列出"，恢复后的工具结果消息却没有 `tool_call_id`，配对被破坏——这属于"看着修好了、实际更糟"，与 stubfix-02 的禁止假成功同源。

**为什么不做就地改写**：执行计划明确"只读，不就地改写"。改写会在用户目录里批量重写历史文件，且一旦投影有偏差就是不可逆的数据损失。投影只在内存中构造 `SessionData`，磁盘字节不变。

## 决策 [必填 - 含为什么]

1. **决策 1（repr → Json 的递归下降投影，失败即放弃）**：新增 `lib/agent/session_legacy_repr.mbt`，把 Debug-repr 文档投影成 `Json`；仅在裸 JSON 解析失败时回退到它；解析不到文档结尾返回 `None`。
   - **为什么**：复用既有 `SessionData`/`Message` 解码路径（不写第二套解析器）；"整份到结尾"是把"猜错内容"变成"诚实报不可读"的闸门。
2. **决策 2（`String(...)` 体按结构而非转义终结）**：体内括号成对抵消；`depth == 0` 的 `)` 仅当其后的非空白字符是 `,` `}` `]` 时才作为终结。
   - **为什么**：repr 不转义正文，存在 `)` 出现在文本中的真实案例（7 个转储里的 system prompt 正文即含裸 `)`）；该规则是在真实语料上验证过的。
3. **决策 3（消息级 Option 包装容忍，抽三个助手）**：`opt_message_string` / `opt_message_bool` / `opt_message_tool_calls`，与 `opt_string_field` 同宽容度；`tool_calls` 额外接受 `[[...]]`（取内层）与 `[null]`（视作 None）。
   - **为什么**：同一根因（旧序列化器）不应在消息级另行"局部打补丁"；三个助手把宽容规则集中一处，后续新增字段可复用。
4. **决策 4（`ToolCall` 接受 `type_` 别名）**：`type` 缺失时回退读 `type_`，仍缺失则默认 `"function"`。
   - **为什么**：旧文件里两种键名都存在，只认一个会把旧写法的调用降级成默认值（丢掉真实类型信息）。
5. **决策 5（`SessionData` 缺字段容忍）**：`name`/`working_dir` 缺失给 `""`，`stats` 缺失或解码失败给零值，`created_at` 接受数字（epoch ms，既有 `normalize_created_at` 已会转换）。
   - **为什么**：区分"文件不是会话"与"文件是老会话"。`session_id`/`messages` 仍是硬要求（缺它们不算会话）；把可选展示字段的缺失升级为"整份丢弃"，正是本 WP 要消灭的那类静默消失。
6. **决策 6（README 改为精确表述而非"已验证兼容"）**：写清"已验证：旧版转储 + 字段变体（参考机 32/32）；未验证：上游 Ruby 原始样本（不在手）"。
   - **为什么**：执行计划的 DoD 原话是"可升级为'已验证只读兼容'"，但在**没有上游样本**的前提下宣称"上游兼容已验证"就是新的不诚实。宁可把已验证/未验证的边界写清楚，也不换一个更好听的说法。
7. **决策 7（测试用脱敏合成夹具，不搬真实内容）**：`session_legacy_repr_wbtest.mbt` 的夹具按真实 dump 的**结构**造（裸换行、体内裸 `)`、epoch ms、`[string]` 包装），正文自拟；真实文件里的 system prompt 含 CONFIDENTIAL 品牌内容，不得入库。
   - **为什么**：既锁住真实语法难点，又不把品牌机密写进仓库。
