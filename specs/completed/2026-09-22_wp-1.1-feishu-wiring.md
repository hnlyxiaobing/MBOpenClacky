## 问题描述 [必填]

飞书适配器发送侧仍是诚实 stub：`FeishuAdapter::update_message` 报 not implemented，`FeishuApiClient` 的 `send_message`/`update_message`/`upload_image`/`upload_file`/`download_resource`/`fetch_chat_history` 六个方法均返回 "not yet wired to HTTP transport" 错误。`FeishuAdapter::send_text` 虽已接线（走 `build_send_request` + `http_post_json`），但其请求体构建存在契约错误（见现状分析缺陷 1），真实 API 调用会失败。接收侧（webhook 路由、challenge、`parse_event` 富文本解析）已由 stubfix-01 接通，无缺口。

### 详细分析

**缺陷 1（send/update 请求体契约错误）**：飞书 Open API `POST /im/v1/messages` 的契约是 `{"receive_id":"...", "msg_type":"text", "content":"{\"text\":\"...\"}"}`——`content` 必须是**字符串化的 JSON**。`build_feishu_text_content`/`build_feishu_card_content` 正确返回了 `{"msg_type":..., "content":"<字符串>"}` 形状，但 `build_send_request`（`feishu_api.mbt:152-153`）把整个返回对象作为 `content` 值再放进 payload，产生 `content:{"msg_type":..., "content":"..."}` 双层嵌套；`build_update_request`（`feishu_api.mbt:210-213`）同样把对象放进 PATCH body（应为 `{"content":"<字符串>"}`）。`send_text` 从未对真实 API 跑通过，此缺陷未暴露。

**六函数接线现状**：所有函数的请求构建（URL/headers/body）骨架已写好（`build_send_request`/`build_update_request` 已存在；upload/download/history 的 URL 与 headers 在函数内已构建），只差最后的 HTTP 调用与响应解析，与 WP-1.5 媒体接线前的状态同构。

**HttpMethod 扩展影响面**：`grep HttpMethod::` 仅 `lib/web/handlers_channels_wiring_wbtest.mbt:83` 使用 `HttpMethod::Post`（不受影响）；穷尽 match 仅 `http_method_str`/`http_request_method` 两处（需补分支）。

## 决策 [必填 - 含为什么]

1. **决策 1（PATCH 支持）**：给 `lib/client` 的 `HttpMethod` 枚举加 `Patch` 变体，补齐 `http_method_str`/`http_request_method` 映射；在 `lib/channel/http_helper.mbt` 新增 `http_patch_json`（对齐既有 `http_post_json`/`http_get_json` 模式）。
   - **为什么**：底层 `@http.RequestMethod` 已支持 `Patch`（验证记录），本仓枚举只是历史缺口；不扩展则 `update_message` 无法诚实接线（飞书编辑消息只有 PATCH 端点）。
2. **决策 2（修正 content 契约）**：`build_send_request` 改为从构建器返回值中取 `msg_type` 与字符串化的 `content` 平铺进 payload（`content` 为 String JSON）；`build_update_request` 的 PATCH body 改为 `{"content":"<字符串>"}`。为 `build_send_request` 补 payload 形状 wbtest（现有 `build_feishu_text_content` 结构测试不受影响）。
   - **为什么**：与飞书 Open API 公开契约一致；这是行为保真修正而非顺手重构——不修则 send/update 对真实 API 必失败，接线即假成功。
3. **决策 3（六函数接线方式）**：全部走 `@client` 异步传输：send/update 走 `http_post_json`/`http_patch_json`；upload 走手工 multipart（参考 `build_multipart_audio_body`）+ `http_post_bytes`；download 走 `http_get_bytes` + `@base64.encode` 返回（维持函数文档承诺的 "base64 for binary"）；history 走 `http_get_json`。
   - **为什么**：WP-1.5 已验证该组合可行；计划中"multipart 受限则留台账"的前提已被 WP-1.5 的 multipart 能力解除，无需降级。
4. **决策 4（upload 签名 Bytes 化）**：`upload_image`/`upload_file` 的数据参数从 `String` 改为 `Bytes`（零调用方，无兼容负担），multipart 文件段按原始字节写入，文本字段 UTF-8 编码。
   - **为什么**：图像/文件是二进制，String 路径会损坏字节；与 `http_post_bytes` 的 Bytes 语义对齐。
5. **决策 5（业务错误码检查）**：所有 JSON 响应在 HTTP 2xx 后追加 `code != 0` 检查（飞书 v1 接口业务失败也返回 HTTP 200），错误映射 `ChannelError("Feishu ... failed: " + extract_api_error(json))`，与 `send_text` 现有模式一致。
   - **为什么**：不检查 code 就是静默假成功，违反诚实纪律。
6. **决策 6（feishu.mbt update_message + start 注释）**：`FeishuAdapter::update_message` 改为调用 `api_client.update_message` 并做 code 检查；`start()` 的 TODO 注释改为如实描述——webhook 接收已由 HTTP server webhook 路由承担（stubfix-01），长轮询模式不在本期范围。清掉台账行 `feishu.mbt:76` 与 `feishu.mbt:153`。
   - **为什么**：TODO 行在台账中标记为待清缺口，但接收事实已通，保留误导性 TODO 不诚实；长轮询是独立工作包（台账登记，不混入）。
7. **决策 7（测试策略）**：单元 wbtest 覆盖 payload 形状、multipart 构建、响应解析（成功/业务错误/HTTP 错误/base64 往返）；另用一个 `async test` + 本地 raw TCP mock server（参考 `test/e2e/mock_llm_server.mbt`）对六个方法各跑一次真 HTTP 往返（`FeishuApiClient::with_base_url` 指向 `127.0.0.1` 随机端口），mock 断言收到的方法行/路径/headers/body。
   - **为什么**：DoD 要求 HTTP 路径经本地 mock 跑通；无真实飞书凭据，mock 是最高保真验证。
