## 问题描述 [必填]

`README.md`/`CLAUDE.md`/`docs/improvement-roadmap.md` §2.3 把「真模型能力评测」列为项目**自己立项的稀缺项**（"mock LLM 测试无法回答真模型能否干活"），但落地状态是：

1. `cmd eval --live` **完全未接线**：`cmd/eval.mbt:75-87` 打印三段说明后 `@sys.exit(1)`，帮助文本（`cmd/main.mbt:198`）与契约探针（`cmd/selftest.mbt:520`）都把这一"诚实不可用"固定成判据。
2. **任务集不存在**：`test/capability/` 只有 README，没有 `tasks/` 目录——规程定义了任务 schema（`test/capability/README.md` 22-31 行）却没有任何一条任务。
3. **运行器不存在**：全仓无"真模型驱动 harness"的任何符号；现有 `test/eval/tool_harness.mbt` 只支持脚本化 `steps`（模型不参与决策）。
4. 因此**本环境从未执行过任何真模型评测**，台账「真模型评测波动」一行只能记"harness 就绪、真模型未执行"。

本 WP 的目标是消除这一"宣传 > 现实"的中间态：让一条命令用真实 key 跑出可重跑的评分向量与成本证据，且**无 key / 无任务时仍诚实报错**（不回退到假成功）。

### 详细分析

四层现状（层 8 真模型能力基准，口径见 `docs/testing.md:19`）：

- **规程层已定**：任务 schema、判分口径、纪律（不进 CI / 不写 key / 任务集只增不减）都写在 `test/capability/README.md`，本 WP 不重新设计口径。
- **判分原语已实现且进 CI**：`test/eval/tool_harness.mbt` 的 `seed` 铺设、`{sandbox}` 展开、四类 `checks`、评分向量（completion/verification/repeatability/cost）与两种报告输出（JSON/markdown）。缺的只是"步骤由模型自主产生"。
- **驱动层缺失**：`cmd/eval.mbt` 的 `--live` 是一个显式占位（决策 D1 回退），无 runner、无任务集。
- **配置层半通**：`MBOPENCLACKY_*` 覆盖已在 `AgentConfig::apply_env_overlay` 就位，但本机 key 在 `DEEPSEEK` 变量里 → 需要一条兜底链，否则"一条命令跑通"在本机不成立。

因此本 WP 的性质是**接线 + 新建任务集**，不是降级声明（roadmap §2.3 建议动作即"接线"）。

## 决策 [必填 - 含为什么]

1. **决策 1：live 驱动落在 `test/eval/live_harness.mbt`，runner 以异步闭包注入，真 runner 由一个工厂函数提供。**
   为什么：`test/eval` 已是"被 cmd 复用的 harness 库"（`cmd/moon.pkg` 已依赖它），把驱动放在这里可与判分原语同源、可 wbtest；把 runner 参数化后，"逐 trial 沙箱 → 跑 N 次 → 跑 checks → 计分 → 出报告"这段**无需网络即可确定性测试**（注入假 runner），而唯一不可离线的部分（真 Agent 循环）缩到一个工厂函数里，并且可以对着 `test/e2e` 的 `MockLlmServer` 做端到端验证（决策 6）。反过来，如果把 runner 写在 `cmd/`，则 cmd（executable）无法被任何测试复用，只剩"真 key 手工跑"一条验证路径——不符合项目对新增功能的测试要求。

2. **决策 2：live 评测只暴露与 offline 同构的工具白名单（`file_reader`/`write`/`edit`/`grep`/`glob`），通过**重建受限 ToolRegistry**实现（而非只设 `Agent.allowed_tools`）。**
   为什么：`auto_approve` 下 `should_auto_execute` 恒为 `true`（已验证 `tool_executor.mbt:61-65`），即**模型自主决定的一切工具都会自动执行**——包括 `terminal`/`shell` 别名。真模型在本机沙箱里拿到 shell 能力，既可能破坏沙箱外文件，也使"能力评测"的变量失控。已验证 `llm_caller.mbt:802` 用 `tool_registry.all_definitions()` 产出模型可见工具、`get_resolved` 用同一 registry 解析执行，故**一处过滤同时收紧"可见面 + 可执行面"**，不需要动 `lib/agent`，也不需要发明第二套权限机制。附带收益：live 与 offline 的工具面一致，两个数字可比。

3. **决策 3：live 的模型配置解析顺序为 `MBOPENCLACKY_*`（含 `config.toml`）→ `DEEPSEEK_API_KEY`/`DEEPSEEK` 兜底；兜底默认 `base_url=https://api.deepseek.com`、`model=deepseek-flash`，均可用 `DEEPSEEK_BASE_URL`/`DEEPSEEK_MODEL` 覆盖。**
   为什么：
   - 主链复用既有 `AgentConfig::load_default()`（`MBOPENCLACKY_*` 已在 `apply_env_overlay` 就位），零改动即符合项目约定，不另造一套优先级。
   - 兜底默认值取**实测存在**的模型：本机 key 的 `/models` 只返回 `deepseek-flash` 与 `deepseek-v4-pro`，`deepseek-chat` **不可用**——若照搬 `provider.mbt` 的 legacy 预设默认（`deepseek-chat`）会必然 404。`deepseek-flash` 亦经 curl 实测可返回合法 `tool_calls`，且属廉价档（符合计划的"廉价模型"纪律）。
   - 兜底**只在 live 路径生效**（不改 `lib/config`）：`DEEPSEEK*` 是本机便利，不是产品级 provider 约定；把它塞进全局前缀链会改变 `mbopenclacky -m` 的行为，属范围外扩张。
   - 三者都缺失 → **诚实报错并说明如何配置**（exit 1），不退化成"跳过评测但 exit 0"。

4. **决策 4：评分向量的 `cost_usd` 用 `RunResult.total_cost_usd` 累加，并在报告中标注 `cost_source`（`Estimated` 即项目自身估算）；token 用量由 `UsageUpdated` 事件汇总。**
   为什么：`RunResult` 已携带真实成本与来源（比另算一份更可信）；`CacheStats` 无 token 总量（已读结构，只有 cache 类计数），故 token 走事件汇总，取不到就如实显示 0——不编造。

5. **决策 5：退出码语义——0 = 评测批次跑完且无基础设施失败；1 = 无 key / 无任务 / 参数非法 / 任一 trial 的 agent 运行以 `Error` 结束。**
   为什么：空跑/断网/auth 失败属"命令没完成"，必须非零（诚实纪律）；而**任务断言未通过是评测数据，不是命令失败**，故不置 1（否则每次真模型波动都像 CI 红，与"不进 CI 的统计基准"定位矛盾）。两种情况的完整证据都进 stdout 的单一 JSON 对象（含 `infrastructure_errors` 与逐 trial 明细），不靠退出码传递信息。

6. **决策 6：端到端验证用两层证据：(a) wbtest 注入假 runner 覆盖驱动逻辑；(b) wbtest 用 `test/e2e` 的 `MockLlmServer` 驱动**真** runner（真 Agent + 真工具 + 真沙箱），再 (c) 用户本机真 key 手工跑一次并如实记录波动与成本。**
   为什么：(b) 能在无网络、无 key 的前提下证明"prompt → ReAct → 工具 → 沙箱 → checks → 计分"整链真的通了（这是 mock LLM 的正当用途，`test/capability/README.md` 的纪律禁止的是"用基准替代 mock 链路测试"，不是禁止 mock 验证接线）；(c) 才是 WP 的 DoD 硬证据，且必须如实记录波动而非只报好数字。

7. **决策 7：契约探针（`cmd/selftest.mbt`）改为断言**与 key 无关**的确定性失败路径：`eval --live --repo <不存在>` → exit 1 + `no task files found`；`eval --offline --live` → exit 2 + `mutually exclusive`。**
   为什么：探针继承进程环境（已验证），若沿用"带有效 repo 的 `--live`"，在本机（有 `DEEPSEEK`）会**真的发起付费 API 调用**——契约探针变成计费动作，不可接受；若断言"无 key 报错"，则在有 key 的机器上必然失败，探针不稳定。改断言"参数/输入校验先于模型解析"这一确定性契约，既覆盖"`--live` 不再是 not implemented 的占位"，又保证任何机器/CI 上都一致。**无 key 时的诚实报错**改由 `cmd` 侧 wbtest 控制环境变量断言（确定性）。

## 对抗性审核记录

**复核结论（2026-09-22）**：

1. **推翻失败（假设成立）**：初稿假定"照搬 provider 预设默认即可"——用 curl 打 `https://api.deepseek.com/models` 实测后**推翻了自己的初稿**：该账号可用模型只有 `deepseek-flash`/`deepseek-v4-pro`，`deepseek-chat`（legacy 预设默认）与 `deepseek-v4-flash`（v4 预设列出的名字）**都不在列表内**。据此改为默认 `deepseek-flash`，并把"预设列表 ≠ 账号可用列表"写进决策 3 的理由，避免实现时照抄预设。
2. **推翻失败（假设成立）**：担心 `deepseek-flash` 只支持纯文本、不支持 tool_calls（那样评测无意义）——实测 `/chat/completions` 带 `tools` 返回 `finish_reason":"tool_calls"` 与合法 arguments，疑虑解除（证据见验证记录）。
3. **发现并修正设计缺陷**：初稿只打算 `agent.allowed_tools = Some([...])` 限制工具。复核发现 `should_auto_execute` 在 `AutoApprove` 下恒真，而**执行解析走的是 `tool_registry.get_resolved`**（`test/eval/tool_harness.mbt:346` 与 `registry.mbt:223`），`allowed_tools` 只影响发送给模型的 definitions（`llm_caller.mbt:802` 用的是 registry 不是 allowed_tools）。若模型幻觉出一个未在 definitions 中的工具名，仍可能被 registry 解析并自动执行。故改为**重建受限 registry**（一处同时收紧可见面与可执行面），并保留 `allowed_tools` 不作为唯一防线。这是本 spec 最重要的安全修正。
4. **发现并修正设计缺陷（探针计费）**：初稿打算沿用"`eval --live` 无 key → 诚实报错"作为探针。复核 selftest 引擎后确认**探针继承父进程环境且不清环境**，在本机（`DEEPSEEK` 已设）该探针会真的发起付费请求。改为断言与 key 无关的确定性路径（`--repo 不存在` → no task files；`--offline --live` → 互斥），并把"无 key 报错"下沉到可控制环境的 wbtest（决策 7）。
5. **推翻失败（假设成立）**：担心 `test/eval` 加 `test/e2e` 依赖会成环——核对 `test/e2e/moon.pkg`（依赖 `lib/message`/`lib/agent`/`lib/client`/`lib/config` + wbtest 的 `test/diff`）后确认 e2e 不依赖 eval，无环；且 `cmd` 已同时依赖两者，属既有同级模式。
6. **纠正范围**：初稿把 `lib/config` 的 DeepSeek 前缀兜底列进改动范围，复核后判定为范围外扩张（会改变 `mbopenclacky -m` 行为，且本机便利不等于产品约定），改为只在 `cmd/eval_live.mbt` 内实现，明确列入"不涉及文件"。
7. **未发现反例**：判分原语（`seed`/`{sandbox}`/四类 checks）、`Agent::run`、`RunResult` 成本字段、`HookEvent` 观测面、`docs/eval` 可创建性、`cmd/moon.pkg` 既有依赖、OpenAI 兼容 URL 形状（`{base}/chat/completions`）均经复核确实在位。
