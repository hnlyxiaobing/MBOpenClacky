## 核心目标

评估并规划让 MBOpenClacky 能在 `wasm-gc` 目标上构建/运行，消除"`moon test --target wasm-gc` 失败于 FFI"的阻塞，为浏览器/边缘端部署打开可能。

## 关键能力

- 识别所有阻塞 wasm-gc 的 FFI 依赖（`tty`、`crescent`、`lib/client/http_native.c`、`lib/brand/crypto_native.c`）。
- 给出"哪些可条件编译替换、哪些必须降级或 stub"的清单。
- 产出一份"是否值得做、怎么做、做到哪一步"的决策结论（可暂缓）。

## 明确不做

- 不在本轮实现完整 wasm 运行时（原因：需先有可行性结论）。
- 不替换 tty/crescent 的 native 实现（原因：可能影响现有 TUI/native 主路径，需评估后再决定）。
- 不引入 wasm 专用 HTTP/加密库（原因：待可行性确认后由后续 spec 处理）。

## 关键决策（含为什么）

1. **先评估后实现**：wasm-gc 涉及多个 FFI 边界，盲目替换风险高，先产出决策。
2. **聚焦非 TUI 子集**：TUI 强依赖 tty，wasm 场景下 TUI 无意义；评估范围限定"Web 后端 + Agent 核心 + LLM 客户端"子集是否可单独 wasm 化。
3. **加密降级可接受**：wasm 端若用 WebCrypto 提示或限制品牌功能，需文档化。
4. **默认姿态是"探索性"**：若结论为当前不值得做，本 spec 输出"暂缓 + 触发条件"，不强制推进。
